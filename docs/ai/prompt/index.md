# AI 提示词

提示词（Prompt）是用户与大语言模型交互时输入的指令文本。写好提示词的核心不是背诵固定咒语，而是把「角色、任务、上下文、输出格式、约束」这几个要素组织清楚。本页记录提示词的基础概念、常用技巧和可复用的场景模板。

> 提示词的效果因模型版本和任务类型而异，以下内容是通用思路而非万能公式，实际使用时需要结合具体模型迭代调整。

## 基础概念

一个结构完整的提示词通常包含以下要素：

| 要素 | 作用 | 示例 |
| --- | --- | --- |
| 角色 | 约束模型回答的视角和口吻 | 「你是一位资深前端工程师」 |
| 任务 | 明确要做什么 | 「请审查下面的代码」 |
| 上下文 | 提供背景信息，减少模型自由发挥 | 技术栈、项目背景、目标读者 |
| 输出格式 | 规定返回结构，便于解析 | 「以 Markdown 表格输出」 |
| 约束条件 | 划定边界，避免不想要的输出 | 「不要引入新依赖」 |

不需要每次都写全五个要素，但**任务必须具体**。对比：

```text
帮我优化一下这段代码
```

```text
你是一位资深 TypeScript 工程师。
请优化下面的工具函数，要求：
1. 补全参数和返回值的类型标注，不使用 any；
2. 保持函数签名不变；
3. 只输出优化后的代码，不需要解释。
```

后者的输出质量和可控性明显更好，因为模型不需要猜测「优化」的定义。

## 常用技巧

### 清晰具体的指令

把模糊形容词换成可验证的标准。「写得简洁一点」不如「控制在 200 字以内」；「专业一点」不如「面向有三年经验的前端工程师，使用规范术语」。

### 用分隔符隔离上下文

当提示词里包含大段参考材料时，用分隔符明确「指令」和「材料」的边界：

```text
请总结三引号内文章的核心观点，输出为不超过 5 条的中文列表：

"""
（这里粘贴原文）
"""
```

常见分隔符有 `"""`、XML 标签（`<article></article>`）、`---` 等，形式不关键，关键是让模型能区分指令与数据。

### 少样本示例（Few-shot）

先给一两个输入输出示例，再让模型按示例处理新输入，适合格式敏感的任务：

```text
将下面的提交信息改写为规范化格式，参考示例：

输入：修了个登录的bug
输出：fix(login): 修复登录状态下 token 过期未刷新的问题

输入：加了暗黑模式
输出：feat(theme): 新增暗黑主题模式与切换入口

现在处理：
输入：更新了依赖
输出：
```

### 思维链（Chain of Thought）

对推理类任务，要求模型先分步分析再给结论，可以减少跳步错误：

```text
请一步步分析这段代码的时间复杂度，说明每一步的推导过程，最后单独给出结论。
```

### 迭代优化

提示词很少一次写好。推荐的迭代流程：

1. 先用最简单的指令跑一遍，看输出差在哪里；
2. 针对不满意的地方追加约束（太长就限字数，跑题就补上下文，格式乱就给示例）；
3. 每次只改一个变量，确认改动是否有效，避免「改了很多但不知道哪条起作用」。

## 场景模板

以下模板可直接复制后替换占位内容使用。

### 代码生成

```text
你是一位资深前端工程师。
请用 {技术栈，如 Vue 3 + TypeScript} 实现以下功能：
{功能描述}

要求：
1. {具体要求，如：组件拆分合理、事件命名清晰}；
2. 代码中的注释使用中文；
3. 先给出文件结构，再给出完整代码。
```

当代码生成任务有明确的交付形态和质量标准时，可以把约束写得更完整。下面是一个创意编程（3D 可视化）的进阶范例，输出格式、资源、交互、性能、可维护性全部是可验证的要求：

```text
帮我做一个单文件的 HTML 网页，用 Three.js 实现一个可以自由浏览的 3D 场景。

场景是：
【你想要的画面，越具体越好。比如：重庆洪崖洞的夜景，层层叠叠的吊脚楼亮着暖黄色的灯，前面是嘉陵江，江上有游船，旁边是千厮门大桥，远处是城市的楼群】

要求：
1. 所有模型和贴图都用代码生成，不要引用任何外部的图片和模型文件；
2. 支持鼠标拖动旋转视角、滚轮缩放；
3. 画面要有氛围感，重点处理光照、雾气和色调；
4. 在普通的笔记本上也要流畅，加载的时候显示进度；
5. 主要物体都做成独立的组件，方便我后面单独修改。
```

注意【】里的场景描述是变量：约束固定、创意可替换，换一段画面描述就能复用整段模板。

### 视觉评审循环

面向视觉类产出（页面、3D 场景、海报等）的自动迭代工作流。它与一次性提示词不同，编排的是「实现 → 截图 → 独立评审 → 修改」的收敛循环，与上面的创意编程模板天然配对：

```text
每改完一版，用浏览器打开它，从几个固定的角度各截一张图。

再开一个子 Agent，只给它看截图，不给它看代码，
让它以一个挑剔的美术指导的角度，按严重程度列出画面问题。

你按它的意见改，一直改到它只剩小问题为止。
```

这段提示词的四个关键设计：

1. **只给截图不给代码**：强制评审从最终效果出发，防止被实现细节带偏，是「分隔符隔离上下文」在评审场景的变体；
2. **评审角色化**：「挑剔的美术指导」用苛刻人设拉高验收标准——角色要素用在评审方而非执行方；
3. **实现与评审分离**：子 Agent 只负责挑毛病，避免「自己改自己审」的确认偏差，对应开发中的 author / reviewer 分工；
4. **可验证的终止条件**：「只剩小问题」给循环明确的收敛信号，避免无限迭代。

「固定的角度」同样重要：每轮评审输入一致，问题才可对比、可验证收敛。

### 代码审查

```text
你是一位代码审查者。
请审查下面的代码，按以下维度逐项给出意见：

1. 正确性：是否有逻辑错误或边界问题；
2. 可读性：命名与结构是否清晰；
3. 性能：是否存在明显的性能问题；
4. 安全性：是否存在注入、XSS 等风险。

对每个问题标注严重程度（高 / 中 / 低），并给出修改建议。
没有问题的维度直接写「无」。

"""
{粘贴代码}
"""
```

### 文档总结

```text
请总结下面的文档，输出结构：

## 一句话概括
{...}

## 核心要点
{不超过 5 条}

## 值得注意的细节
{容易被忽略但重要的信息}

用简体中文输出，保留关键术语的英文原文。

"""
{粘贴文档}
"""
```

### 翻译润色

```text
请将下面的英文技术文章翻译为中文：

1. 专业术语保留英文（如 hook、tree shaking）；
2. 符合中文技术文档的表达习惯，不要逐词直译；
3. 译文后单独列出你不确定如何翻译的术语对照表。

"""
{粘贴原文}
"""
```

### 项目审计与治理

面向 AI 编码助手的全仓库治理任务，与针对单段代码的审查不同，要点是**用枚举词定义问题边界，并约定分级行动**：让助手自主处理有把握的部分，不确定的部分只汇报不动手，人工兜底。最简形式只需要两句话：

```text
阅读这整个项目，找出所有损坏的、不一致的、低效的、或者不再需要的内容。

修复你有把握的部分，把剩下的列出来供我审查。
```

需要更可控的输出时，可以扩展为结构化版本：

```text
请审计整个项目，范围包括源码、配置和文档。

问题定义（按以下四类查找）：
1. 损坏的：无法运行、引用不存在的文件或路由；
2. 不一致的：同类内容写法或风格互相矛盾；
3. 低效的：明显可简化或存在重复的部分；
4. 不再需要的：失效链接、过时内容、无引用的孤立文件。

处理规则：
1. 有把握的问题直接修复，并逐条说明改了什么、为什么；
2. 没把握的部分不要改动，列成清单附上理由，供我审查后决定。
```

::: tip 适用性说明
仓库级审计的范围越大，越要注意让助手「小步提交、逐项汇报」，一次性放开全仓库自动修改容易误伤无关内容。
:::
