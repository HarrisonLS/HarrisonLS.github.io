AI 提示词 ​

提示词（Prompt）是用户与大语言模型交互时输入的指令文本。写好提示词的核心不是背诵固定咒语，而是把「角色、任务、上下文、输出格式、约束」这几个要素组织清楚。本页记录提示词的基础概念、常用技巧和可复用的场景模板。

提示词的效果因模型版本和任务类型而异，以下内容是通用思路而非万能公式，实际使用时需要结合具体模型迭代调整。

基础概念 ​

一个结构完整的提示词通常包含以下要素：

要素作用示例
角色约束模型回答的视角和口吻「你是一位资深前端工程师」
任务明确要做什么「请审查下面的代码」
上下文提供背景信息，减少模型自由发挥技术栈、项目背景、目标读者
输出格式规定返回结构，便于解析「以 Markdown 表格输出」
约束条件划定边界，避免不想要的输出「不要引入新依赖」

不需要每次都写全五个要素，但任务必须具体。对比：

text
帮我优化一下这段代码
1
text
你是一位资深 TypeScript 工程师。
请优化下面的工具函数，要求：
1. 补全参数和返回值的类型标注，不使用 any；
2. 保持函数签名不变；
3. 只输出优化后的代码，不需要解释。

常用技巧 ​

清晰具体的指令 ​

把模糊形容词换成可验证的标准。「写得简洁一点」不如「控制在 200 字以内」；「专业一点」不如「面向有三年经验的前端工程师，使用规范术语」。

用分隔符隔离上下文 ​

当提示词里包含大段参考材料时，用分隔符明确「指令」和「材料」的边界：

text
请总结三引号内文章的核心观点，输出为不超过 5 条的中文列表：

"""
（这里粘贴原文）
"""

迭代优化 ​

提示词很少一次写好。推荐的迭代流程：

  1. 先用最简单的指令跑一遍，看输出差在哪里；
  2. 针对不满意的地方追加约束（太长就限字数，跑题就补上下文，格式乱就给示例）；
  3. 每次只改一个变量，确认改动是否有效，避免「改了很多但不知道哪条起作用」。

视觉评审循环 ​

面向视觉类产出（页面、3D 场景、海报等）的自动迭代工作流。它与一次性提示词不同，编排的是「实现 → 截图 → 独立评审 → 修改」的收敛循环，与上面的创意编程模板天然配对：

text
每改完一版，用浏览器打开它，从几个固定的角度各截一张图。

再开一个子 Agent，只给它看截图，不给它看代码，
让它以一个挑剔的美术指导的角度，按严重程度列出画面问题。

你按它的意见改，一直改到它只剩小问题为止。

4

这段提示词的四个关键设计：

  1. 只给截图不给代码：强制评审从最终效果出发，防止被实现细节带偏，是「分隔符隔离上下文」在评审场景的变体；
  2. 评审角色化：「挑剔的美术指导」用苛刻人设拉高验收标准——角色要素用在评审方而非执行方；
  3. 实现与评审分离：子 Agent 只负责挑毛病，避免「自己改自己审」的确认偏差，对应开发中的 author / reviewer 分工；
  4. 可验证的终止条件：「只剩小问题」给循环明确的收敛信号，避免无限迭代。

「固定的角度」同样重要：每轮评审输入一致，问题才可对比、可验证收敛。

项目审计与治理 ​

面向 AI 编码助手的全仓库治理任务，与针对单段代码的审查不同，要点是用枚举词定义问题边界，并约定分级行动：让助手自主处理有把握的部分，不确定的部分只汇报不动手，人工兜底。最简形式只需要两句话：

text
阅读这整个项目，找出所有损坏的、不一致的、低效的、或者不再需要的内容。

修复你有把握的部分，把剩下的列出来供我审查。
1
2
3

需要更可控的输出时，可以扩展为结构化版本：

text
请审计整个项目，范围包括源码、配置和文档。

问题定义（按以下四类查找）：
1. 损坏的：无法运行、引用不存在的文件或路由；
2. 不一致的：同类内容写法或风格互相矛盾；
3. 低效的：明显可简化或存在重复的部分；
4. 不再需要的：失效链接、过时内容、无引用的孤立文件。

处理规则：
1. 有把握的问题直接修复，并逐条说明改了什么、为什么；
2. 没把握的部分不要改动，列成清单附上理由，供我审查后决定。
